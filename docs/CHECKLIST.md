## 1. 실격 사유 — 절대 어기면 안 되는 것

### 1-1. 행 독립 추론 (규칙 4) ★가장 중요

`test.csv`의 각 행은 **독립적으로** 예측해야 한다. 다른 행이나 전체 분포를 쓰면 실격.

**금지 (공식 명시)**
- `test.csv` 내부 행들로 만든 선수별/팀별/월별 누적 통계
- `test.csv` 내부 빈도값 또는 분포 통계
- `test.csv` 내부 target encoding
- `test.csv` 행 순서 기반 rolling / expanding
- **평가 데이터 전체를 보고 만든 사후 보정값**

**우리 코드가 지키는 방식**

| 위치 | 연산 | 판정 |
|---|---|---|
| `add_features()` | 같은 행 안의 컬럼 사칙연산만 | 안전 |
| `pre.transform()` | 인코더/중앙값이 **학습 시점에 확정**되어 pkl에 저장됨 | 안전 |
| `offset` | `logit(0.4747)` 상수 하나. `train.csv` 시즌 추세로만 산출 | 안전 |
| `np.mean(..., axis=0)` | **모델 5개**의 평균이지 행끼리 아님 | 안전 |

검사 명령:
```bash
grep -nE "groupby|value_counts|rolling|expanding|quantile|describe" script.py
# → 아무것도 안 나와야 정상
```

> ⚠️ 개발 초기에 `p - (p.mean() - r_hat)` 방식을 시도했다가 폐기했다.
> `p.mean()`은 test 전체 예측의 평균이라 **명백한 위반**이다. 최종 코드에는 없다.

### 1-2. 리더보드로 상수 튜닝 금지

**Private Score = 대회 종료 시점의 Public Score** (같은 데이터).
따라서 오프셋만 바꿔 여러 번 제출해 최적값을 찾는 행위는 사실상 평가 데이터의
평균 기저율을 역산하는 것 → 규칙 4 및 "평가 데이터셋 유출" 조항에 저촉.

현재 오프셋은 `train.csv`만으로 산출되며 근거가 코드에 남아 있다. **유지할 것.**

### 1-3. 사용 금지 정보

### 3-3. `requirements.txt`가 한 줄인 이유

공지에 상충하는 두 지시가 있다 — "필요한 모든 패키지 포함" vs "서버 기본 패키지는 넣지 말 것 권장".
**"서버에 없는 것만"이 정답.**

| 필요 | 용도 | 서버 기본 |
|---|---|---|
| joblib 1.5.3 | pkl 로드 | ✅ |
| numpy 1.26.4 | sigmoid, 평균 | ✅ |
| pandas 2.0.3 | csv, 파생 피처 | ✅ |
| scikit-learn 1.8.0 | pkl 안의 ColumnTransformer 등 | ✅ |
| scipy 1.15.3 | sklearn 내부 | ✅ |
| **lightgbm 4.7.0** | pkl 안의 부스터 5개 | ❌ **← 이것만 명시** |

넣으면 위험한 것:
- `pandas==2.3.3` → 서버는 2.0.3, 버전 불일치로 설치 에러
- 버전 없는 `lightgbm` → 최신으로 올라가 pkl 호환 깨짐
- `xgboost` → 안 쓰는데 nvidia-nccl 303MB 동반, 설치 시간 압박

## 5. 검증 방식 — 왜 이렇게 나눴나

실제 과제는 **≤2024 학습 → 2025 예측**, 즉 1년 앞을 맞히는 문제다. 검증도 같은 모양이어야 한다.

```
반복수 결정 : ≤2021 학습, 2022로 early stopping
정직한 평가 : ≤2023 재학습 → 2024 홀드아웃      ← 이 점수만 믿는다
제출용      : ≤2024 재학습 → model/lgbm.pkl
```

**하면 안 되는 것:** 같은 시즌으로 early stopping과 평가를 겸하기. 점수가 낙관적으로 부풀고,
초기에 실제로 이 함정에 빠져 0.006063을 0.005993으로 정정했다.

**2023을 검증 연도로 쓰지 말 것.** 2022→2023에 `game_type=F`(퓨처스, 전체의 10.9%)의 성공률이
0.709 → 0.473으로 반전했다. 전체 기저율 낙폭 -0.029의 거의 전부가 여기서 나온다.
레짐 전환 해라 이 해로 고른 하이퍼파라미터 순위는 2024로 전이되지 않는다.

### 효과가 있었던 것 (성격이 같다)

| 개선 | 효과 |
|---|---|

둘 다 **"모델이 구조적으로 표현할 수 없는 것"**을 넣어준 경우다.
트리는 컬럼 하나씩만 자르므로 두 컬럼의 차·엔트로피를 스스로 못 만든다.
`is_same_hand`, `pitch_entropy`, `form_delta5`가 파생 중 상위였고,
`is_scoring_position`·`quick_motion`처럼 기존 컬럼의 단순 조건 조합은 gain 0.03%로 무의미했다.

### trackman이 실패한 이유 (재시도 금지)

선수 ID 매칭 자체는 **성공했다**. `(season, game_month, game_dayofweek)` 셀별 투구수를
행정규화 → 셀평균 제거 → 좌우별 헝가리안 배정으로 투수 623/792명이 매칭됐고
메인 투구의 95.8%를 커버했다 (매칭에 안 쓴 총 투구수 상관 0.959로 독립 검증).

그런데도 점수가 떨어졌다. **`pitcher_id`가 이미 피처라 트리가 투수 신원을 직접 외운다.**
trackman 집계는 투수당 거의 정적인 값이라 신원 정보와 중복이다. 게다가
`asof_pitcher_success_rate`/`ball_rate`/`middle_rate`는 제구 결과를 직접 측정한 값이고
구속·회전수·릴리스포인트는 그 상류 원인이라, 결과를 이미 가진 상태에선 덧붙일 게 없다.

지표를 릴리스 일관성만으로 줄여도 "투수당 정적 값"이라는 구조가 같아 결과가 안 바뀐다.

## 7. Phase 3 준비물 (Private 상위 약 100명 필수)

- [ ] 학습 코드 개발 환경(OS) 및 라이브러리 버전 → **4절 그대로 기재**
- [ ] Private Score 재현용 학습 코드 → `train.py` (추론 코드는 제출한 `script.py`로 대체)
- [ ] 자유 형식 솔루션 PPT
- [ ] 팀원별 Phase 3 참가 여부 기재
- [ ] 제출처 `dacon@dacon.io`, 인코딩 UTF-8, 확장자 `.py` / `.ipynb`

> Phase 1 미이수자는 Phase 2 성적과 무관하게 Phase 3 참가 불가.

PPT 소재는 6절이 그대로 쓸 만하다. 무엇이 올랐는지보다 **왜 대부분이 실패했는지**와
**검증 구조를 어떻게 정직하게 만들었는지**가 설득력 있다.

## 8. 파일 구성

```
lg_ws/
├── train.py            학습/검증 (제출 X)
├── script.py           추론 + 파생 피처 정의 (제출 O)
├── requirements.txt    lightgbm==4.7.0 (제출 O)
├── submit.zip          제출물
├── model/
│   ├── lgbm.pkl        우리 모델 (제출 O)
│   └── rf.pkl          대회 제공 베이스라인 (제출 X, 미사용)
├── data/               train / test / sample_submission / trackman_history
└── output/submission.csv
```

`train.py`가 `script.py`의 `build_features`를 import한다. 파생 피처 정의를 한 곳에만 두어
학습과 추론이 어긋나지 않게 하고, 제출 zip 구조도 그대로 유지하기 위함이다.
**`script.py`는 `train.py`에 의존하지 않는다** (격리 실행 테스트로 확인).
